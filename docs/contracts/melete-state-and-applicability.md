# Melete 상태와 DSE 적용성 연결 계약

이 문서는 Melete `9a3564dd96de22d0311522417c2c36e6bf2a0a91`의 실제 Python 계약을 DSE 어댑터가 해석하는 방법을 고정한다. Melete는 관측·기억·검색 후보를 제공하고, DSE는 버전된 predicate, 출처 권한, 원본 철회, 설계 스냅샷에 대한 적용 결정을 소유한다. 이 문서와 fixture는 설계 oracle이며 구현 또는 실행 증거가 아니다.

## Melete가 제공하는 계약

Melete `Observation`은 `event_id`, `scope`, `observed_at`, `actor`, `kind`, `payload`, `source_ref`, `previous_event_id`, `root_event_id`, `task_family`, `intervention_id`를 가진다. `IntakeContext`는 사용자·namespace·tool·session·cwd·branch 및 task/frame/action/observation 단위의 수집 문맥이다. [고정된 Observation 및 IntakeContext 타입](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/observation.py#L29-L57).

핵심 수집 경로는 `Engine.ingest(Observation, IntakeContext)`이며 scope/actor 확인, 본문 검증, tombstone 확인, 이벤트 canonicalization과 digest 기반 중복 처리를 수행한다. [Engine.ingest 입력 검증과 중복 분기](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L343-L405). 구성된 `CognitionKernel.ingest`는 auth 문맥을 검사한 뒤 Engine에 위임한다. [CognitionKernel.ingest](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/cognition/kernel.py#L205-L241). CLI는 JSONL Observation을 읽어 설정과 인자로 `IntakeContext`를 만들고 receipt를 내보낸다. [실제 `melete ingest` CLI](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/cli.py#L56-L84).

`IngestReceipt.status`는 `stored | trace_only | duplicate`이고 `extraction_incomplete`, `embedding_pending`, `embedding_failure_reason`은 별도 필드다. receipt에는 `memory_ids`, `memory_revision`, `journal_seq`도 있다. [실제 receipt 타입](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/observation.py#L63-L73). 수집 구현은 source event를 journal에 기록한 다음 추출 메모리가 있으면 IDs를 채우고 embedding을 시도한다. 최종 status는 informative 여부로 정하며 trace-only도 원본 event로 남을 수 있다. [source 저장과 gate label](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L454-L497), [메모리 생성과 embedding 등록](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L498-L519), [receipt status와 독립 flags](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L729-L741).

따라서 `stored`만으로는 memory ID, 추출 완결성, embedding 완료 또는 검색 가능성을 증명하지 않는다. `trace_only`는 검색 메모리가 없을 수 있다. `duplicate`는 동일 event와 digest의 기존 결과를 돌려주는 멱등성 결과이므로 독립 evidence 수를 늘리지 않는다. 동일 event ID에 다른 본문은 충돌이다. `extraction_incomplete=true`는 materialized memory가 있어도 완결된 지식 추출을 뜻하지 않는다. `embedding_pending=true`여도 lexical query가 후보를 반환할 수 있고, `false`도 검색 노출의 증거는 아니다. Melete text query는 dense 검색 실패 후 lexical 검색을 수행할 수 있다. [idempotency 동작과 trace-only 예시](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/tests/contract/test_T01_authority_and_idempotency.py#L21-L49), [dense 실패 후 lexical 경로](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L757-L786).

## 다섯 가지 독립 상태와 확인 근거

DSE episode ledger는 한 개의 `ingest_status`로 단계를 축약하지 않는다. 각 상태는 값과 이를 확인한 receipt/query/reference를 함께 가진다.

| DSE 상태 | 확인 규칙 |
|---|---|
| `received` | DSE가 보낸 Observation의 `event_id`를 기록했다. 이는 Melete 저장을 뜻하지 않는다. |
| `persisted` | native receipt의 `journal_seq`와 `memory_revision`을 기록했다. `stored`, `trace_only`, `duplicate`는 저장 결과 유형으로 따로 보존한다. |
| `extracted` | receipt의 `memory_ids`로 materialized memory를 식별한다. `extraction_incomplete=true`이면 `incomplete`; IDs가 없거나 receipt가 없으면 `unknown`/`none_reported`. flag가 false라는 사실만으로 extractor 완료를 주장하지 않는다. |
| `embedded` | receipt의 pending flag는 수집 시 embedding 상태 힌트로만 기록한다. `embedding_pending=true`는 `pending`; false는 `not_pending_at_ingest`다. 실제 적용 판단에서 dense 인덱스 완료를 뜻하지 않는다. |
| `retrieval_visible` | DSE가 기록한 실제 QueryRequest와 host authorization witness가 결합되고, 결과의 query ID/scope/snapshot과 지정한 `(memory_id, version)`이 모두 일치할 때만 `confirmed`. Melete 결과 자체는 authorization 증거가 아니다. |

`MemoryReadout.items`는 retrieval 후보이며 DSE에서 사용 승인을 의미하지 않는다. Melete `QueryRequest`에는 `query_id`, `task_id`, `goal`, scope, payload, scalar context, mode, return format과 time mode가 있다. 각 visibility witness는 그 request의 식별자·scope·context·payload/request digest를 DSE ledger에 고정하고, 결과의 query ID·scope·snapshot과 평가 대상 memory ID/version을 대조한다. [QueryRequest와 ReadoutItem 타입](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/query.py#L58-L86).

Authorization은 query output에서 추론하지 않는다. `CognitionKernel.read(request, auth)`의 `AuthContext`는 host가 공급하는 capability이며 scope ref와 actor를 갖고, read는 auth, host scope와 request scope 일치를 검사한다. DSE ledger는 실제 host call에서 기록한 principal/scope/context binding과 authorization decision/evidence reference를 별도 witness로 보관해야 한다. `MemoryReadout`이나 model-generated JSON의 `authorized=true` 같은 값만으로 witness를 만들지 않는다. [host-supplied AuthContext](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/cognition/contracts.py#L28-L35), [auth/scope check와 query ID idempotency](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/cognition/kernel.py#L292-L324).

QueryRequest의 `context`와 memory `applicability`는 모두 flat `Condition = dict[str, FeatureValue]`이고 string/bool/int/float scalar equality만 표현한다. 키가 없으면 `unknown`, 값이 다르면 `mismatch`, 타입까지 정확히 같으면 `match`다. range, nested field, 비교 연산자 또는 집합 조건을 이 필드에 직렬화하지 않는다. [native Condition 타입](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/memory.py#L9-L10), [match/unknown/mismatch 규칙](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/patterns/conditions.py#L8-L23). Query는 scope 제한 버전 중 후보를 선택하고 snapshot을 기록한다. [readout snapshot 및 결과 구성](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L935-L1057).

`query_binding`의 payload/request digest, principal ref와 auth evidence ref는 DSE bridge ledger의 외부 입력이다. 예시 fixture의 digest 문자열과 principal/evidence ref는 `synthetic_contract_inputs`이므로 실제 query, 사용자, 권한 또는 runtime 증거가 아니다. 운영에서 이를 채우려면 host call 기록과 권한 근거를 같은 query ID 및 response identity에 결합해야 한다.

## DSE predicate binding과 fail-closed 사용

DSE가 predicate authority다. 각 applicable claim/memory 연결에는 DSE ledger의 `predicate_ref`, `predicate_version`, canonical predicate SHA-256, 대상 design snapshot, source event/root, Melete `(user_id, namespace, memory_id, version)`을 묶는다. Melete의 `Scope`는 user ID와 namespace이며 DSE source ACL을 표현하지 않는다. PatternVersion의 `declaration_refs`도 query `ReadoutItem`에 노출되지 않으므로 이 참조의 왕복 보존을 가정하지 않는다. 따라서 binding은 DSE ledger가 권위 있는 형태로 유지한다. [Melete Scope와 memory version](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/scope.py#L8-L14), [memory/pattern 필드와 declaration refs](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/memory.py#L25-L49), [ReadoutItem 반환 필드](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/contracts/query.py#L77-L86).

Melete `Condition`에는 DSE predicate의 의미를 보존하는 정확한 scalar 힌트만 보낸다. 힌트는 native 후보 검색에 쓸 수 있지만 predicate 전체의 증거가 아니며 range/nested/버전 hash authority가 아니다. 검색 이후 DSE는 현재 predicate registry에서 ref, version, hash를 다시 확인하고 전체 predicate를 대상 design snapshot에 평가한다. source ACL, source 철회·supersession, Melete scope, query snapshot freshness도 다시 확인한다. 검색 당시와 사용 시점이 달라졌거나 확인할 수 없으면 후보 자체는 retrieval evidence로 남기되 적용은 `unknown`으로 하고 execution permission은 `denied`로 둔다. Melete applicability 계층도 일부 역할을 candidate reference로 남기면서 적용성 불명인 전략을 분리할 수 있다. [applicability resolution](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/patterns/applicability.py#L64-L117).

다음 조건은 memory 적용을 fail-closed 한다: predicate ref/version/hash가 없거나 오래됨, 복합 predicate를 현재 resolver가 평가할 수 없음, ACL 미확인/철회, 원본 철회 또는 supersession 미해결, query snapshot이 오래됐거나 revision을 확인할 수 없음, episode predecessor/order가 누락됐거나 충돌함. `allowed_unknown_reasons`에는 실제 원인을 남기고 미확인을 false 또는 valid로 승격하지 않는다. 설명과 다음 실험 설계를 위해 retrieved candidate는 보존할 수 있다.

## 실제 입출력 경로와 미지원 동작

현재 확인된 입출력은 Python `Engine.ingest/query`, auth-scoped `CognitionKernel.ingest/read`, CLI의 `melete ingest` JSONL 및 `melete query` JSON request다. [query CLI](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/cli.py#L189-L223). Adapter runtime CLI의 JSON-lines dispatch도 있으나 HTTP 또는 MCP endpoint 계약은 확인되지 않았다. [runtime CLI dispatch](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-adapters/src/melete_adapters/runtime_cli.py#L21-L33). Engine query는 `TextPayload`만 검색하며 vector query는 `unsupported_capability`로 거부된다. [text-only query search](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L757-L762). scope/auth 또는 text query 지원 범위를 구성하지 못하면 DSE bridge도 호출하지 않는다. Query 결과가 없을 때 embedding flag만으로 visibility를 대신 판단하지 않는다.

고정 commit의 core 경로에는 공개 embedding retry/rebuild entrypoint가 없다. ingest 시 실패는 pending으로 기록되며 같은 event를 다시 보내면 새로운 추출/embedding 실행 대신 duplicate receipt가 반환된다. [동기 embedding 등록](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L196-L204), [duplicate receipt 반환](https://github.com/jimmylegendary/melete/blob/9a3564dd96de22d0311522417c2c36e6bf2a0a91/packages/melete-core/src/melete/engine.py#L343-L405). 향후 recovery worker가 필요하면 별도 capability와 재조회 검증을 설계해야 한다. 이 문서는 존재하지 않는 retry endpoint를 정의하지 않는다.

## 연동 시작 조건

첫 DSE episode부터 stable event ID, root/predecessor 관계, immutable artifact reference와 digest, DSE predicate binding, Melete scope, 관측·receipt·query snapshot을 bridge ledger에 남긴다. Melete에 보낼 이벤트를 고를 때 모든 로그를 지식 memory로 승격하지 말고, trace-only 보존과 memory 추출을 별도 정책으로 둔다. 첫 구현은 한 end-to-end trajectory에서 수집→receipt→query 후보→DSE 재검증→실험 outcome의 연결을 증명한 뒤 다른 hardware/kernel/workload 범위로 확장한다. 아래 [melete-bridge.schema.json](https://github.com/jimmylegendary/dse-knowledge/blob/docs/p0-episode-contracts/schemas/melete-bridge.schema.json)와 [melete-cases.json](https://github.com/jimmylegendary/dse-knowledge/blob/docs/p0-episode-contracts/fixtures/p0/melete-cases.json)는 예상 동작을 고정하며, fixture의 `runtime_observation`은 모두 `not_run`이다.
