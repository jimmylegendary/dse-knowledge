06 / STRUCTURAL ONLY
!
HAT committee와 DSE KG는 아직 연결되지 않았습니다. Q2의 native 18/18에는 HAT schema 구조 검사가 포함되지만, committee의 자율 검색·물리 검토·HAT simulation을 통과했다는 뜻은 아닙니다. 아래는 실제 코드를 확인한 연결 설계입니다.

현재 DSE 경로 실제 동작

POST /api/validate/hardware → hat.load_twin → hat.validate_twin

구조 검사만 수행합니다. 결과의 physical_feasibility=not_assessed, buildability=not_asserted를 유지합니다. 별도의 DSE 판단은 검색 1회 → Codex 응답 방식이며, 전문가별 검색 loop는 없습니다.

현재 HAT committee KG 미연결

engine.handle(op="verify_committee") → convene(twin, hat, kb, backend)

기본 지식은 HAT의 verify/knowledge/kb/입니다. 전문가 prompt에 정적 지식과 deterministic findings를 전달합니다. 기본 LLM backend는 단일 claude -p 호출이며 MCP server 목록이 비어 있습니다.

실제 구성은 9개 역할, 5개 scope입니다. 역할이 자신의 scope마다 참여하여 soc 5석·die 6석·package 6석·tray 5석·rack 3석, 합계 25개의 초기 vote를 순차 호출할 수 있습니다. 찬반이 갈리면 해당 scope의 재검토가 있어 최대 50회입니다. 이는 Q2에서 실행하거나 측정한 호출 수가 아닙니다.

목표: 전문가가 필요한 지식을 판단하고 직접 검색 연결 설계 · 미구현

점선 카드는 추가할 연결입니다. KG 주소를 prompt에 적는 것만으로는 이 동작이 생기지 않습니다. 각 expert turn을 이어가는 host tool loop와 read-only KG adapter가 필요합니다.

  1. 검토 입력 고정 →

    rack → tray → package → die/SoC 구성, asset revision, ISA·programming model, workload와 가정을 review manifest로 고정합니다.

  2. 필수 규칙 + 지식 공백 →

    기존 deterministic 검사를 수행합니다. 각 seat는 담당 scope에 빠진 값·제약·근거를 식별합니다. 필수 규칙 전체는 검색 top-k와 독립입니다.

  3. Expert ↔ KG tool 반복 →

    expert가 typed query를 요청하면 host가 기존 검색 API를 호출합니다. 근거가 부족하거나 충돌하면 같은 expert가 추가 검색하고, 한도에 도달하면 unknown을 남깁니다.

  4. 근거 적용성 검사 →

    source·revision·값·단위·조건·사용 목적을 검사합니다. 대상에 맞지 않는 값이나 truncated Claim context는 검증 근거로 자동 승격하지 않습니다.

  5. 의견 → Committee 집계 →

    scope·rule·evidence ID·가정·반례·unknown을 포함한 의견을 모읍니다. 찬성 수와 simulation permission이 물리적 실현 가능성의 증명이 되지는 않습니다.

  6. 기록 → 실험 → 다음 판단

    전문가별 query·근거·수정 요청을 PG/artifact에 보존합니다. 허용된 HAT 실험의 결과·실패와 연결하고 Melete에 경험 reference를 남겨 다음 검토에 조회합니다.

의도한 활용 방식: 공통 evidence 12개를 모든 전문가에게 한 번 배포하는 prefetch만으로 끝내지 않고, 각 seat가 자신의 지식 공백을 해소하도록 검색과 재질의를 수행합니다. 검색 budget·중단 이유·미해결 항목도 기록합니다.

}

판단에는 items의 기술 evidence를 사용합니다. source_results는 탐색 UI용 혼합 결과이므로 그대로 승인 근거로 쓰지 않습니다. 반환 packet에는 원문 locator, material/revision/chunk·Claim reference, 값·단위·조건, role/use policy, retrieval·graph trace와 truncation 여부를 보존해야 합니다. source authority와 현재 설계에 대한 적용 가능성은 별도 검사합니다.

현재 query 최대 2,000자, limit 1–30이며 추가 필드는 금지됩니다. snapshot/platform 필드를 임의로 추가하지 않고 versioned 계약을 먼저 정해야 합니다. cache miss 검색은 외부 embedding을 호출할 수 있어 호출 수·비용도 기록해야 합니다.

별도 상태판정 의미
Simulation permission선언한 가정 아래 탐색 실험을 허용하는가. 불확실성을 명시한 exploratory run은 허용할 수 있습니다.

Review completeness필요한 seat가 근거를 갖고 검토했는가. 전원 abstain은 검토 완료가 아닙니다.
Physical feasibility물리·제조 가능성을 어느 범위까지 확인했는가. 구조 검사나 LLM 찬성만으로 proven이 되지 않습니다.

현재 native HAT는 deterministic error가 없을 때 전원 abstain이어도 approved_with_concerns와 simulation_ready=true를 낼 수 있습니다. 이를 buildability 검증 성공으로 변환하면 안 됩니다. 필수 규칙이 13개라면 evidence top-12 밖의 13번째 실패도 별도 검증 경로에서 검출해야 합니다.

다음 자료 보완: Q2의 28개 source family에는 HAT/HATIR 자체 계약 family가 없습니다. schema·IR·programming model·asset 규약과 실제 fixture/test의 pinned revision을 등록해야 해당 의미에 대한 권위 있는 검색이 가능합니다. 현재 1,000개 자료가 모든 HW 조합 판정을 지원한다고 보지 않습니다.

이 committee의 주 역할은 HW 조합의 buildability 검토이며 PPA는 advisory band입니다. kernel 생성·정확성 검증, HAT 성능 실험, B300 대비 multi-metric 비교는 별도 DSE 경로와 연결해야 합니다. 이번 KG 검색 평가가 그 성능 실험을 대신하지 않습니다.
